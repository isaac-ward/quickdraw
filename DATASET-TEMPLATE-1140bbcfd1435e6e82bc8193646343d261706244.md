# Quickdraw Dataset and Simulator Template

**Code snapshot:** `1140bbcfd1435e6e82bc8193646343d261706244`  
**Status:** current-state audit plus the contract to use for the next environment  
**Scope:** environment, collection, rendering, storage, loading, and the boundary to training/evaluation

## Executive finding

At this commit, Quickdraw has a **batched, Gym-inspired torus simulator feeding a
LeRobot-backed dataset pipeline**. It is not a Gymnasium environment and it is not yet a
simulator-independent dataset generator.

The reusable parts are meaningful: episode-oriented collection, temporal observations and actions,
train-only normalization, video plus low-dimensional data in LeRobot, deterministic split seeds,
and explicit distribution-shift splits. The environment boundary is nevertheless hard-coded at
nearly every layer. A new simulator cannot be plugged in by implementing one interface; it currently
requires edits to generation, metadata, loading, normalization, model modality configuration,
evaluation, visualization, and control.

The collaborator's description of a "gym-style dataset-generating-simulator" is therefore fair only
in the informal sense that `TorusEnv` is stateful and exposes `reset()` and `step(action)`. In the
technical Gymnasium sense it is false:

- `TorusEnv` does not inherit `gymnasium.Env`.
- It defines no `observation_space` or `action_space`.
- `reset()` returns only an observation, not `(observation, info)`.
- `step()` returns only the next observation, not
  `(observation, reward, terminated, truncated, info)`.
- It has no task termination, truncation, reward, registry ID, or wrapper contract.
- It is natively batched, while the Gymnasium single-environment contract is unbatched.

That distinction matters. "Gym-style" describes the surface shape of two method names; it does not
currently provide Gym ecosystem interoperability or environment portability.

## The repository's actual A–D runbook

The initial A–D decomposition is useful, but the current implementation has one important
dependency inversion:

| Protocol | Current implementation | Finding |
|---|---|---|
| **A. Simulator and dataset** | `quickdraw.data_generation` | Torus dynamics, OU actions, FPV rendering, six LeRobot datasets, root metadata. |
| **B. World-model training** | `quickdraw.train_world` | Loads train/val windows and trains one selected world-model variant. |
| **C. Steering/reward training** | `quickdraw.eval_interpret` then `quickdraw.train_reward` | The reward head is trained from world-model latent points and VLM-authored captions, not directly from the simulator dataset. It therefore depends on a trained world model and an interpretation run. |
| **D. Evaluation** | `quickdraw.eval_ood_horizon`, `quickdraw.eval_ood`, `quickdraw.eval_control`, and other post-hoc evaluators | There is no single end-to-end "full experiment" executable. `launch_shootout.sh` launches six B runs; evaluation is a mixture of subscribed in-training routines and separate post-hoc commands. The most direct scientific test of steering is learned-world-model MPPI control, optionally using the language reward head. |

The desired high-level protocol remains A → B → C → D, but the codebase needs an explicit experiment
manifest/orchestrator before D can be called one reproducible "full experiment."

## Current environment contract

### Hidden state, observation, and action

The simulator state for each trajectory is:

```text
(theta, phi, theta_dot, phi_dot)
```

The model never sees these intrinsic angular coordinates. It sees a six-dimensional ambient
observation:

```text
observation_vector = [x, y, z, x_dot, y_dot, z_dot]
```

The first three components lie exactly on a torus in `R^3`; the last three are the corresponding
tangent velocity. The two-dimensional action is:

```text
action = [a_theta, a_phi]
```

Each component is clamped independently to `[-a_max, a_max]`.

### Dynamics

For each angular coordinate, Quickdraw applies semi-implicit Euler integration:

```text
q_dot <- q_dot + dt * (action / mass - gamma * q_dot)
q     <- (q + dt * q_dot) mod 2*pi
```

The resolved base configuration is:

| Parameter | Value | Meaning |
|---|---:|---|
| `R` | 0.75 | Torus major radius |
| `r` | 0.25 | Torus tube radius |
| `dt` | 0.0166667 | Approximately 60 Hz |
| `gamma` | 0.3 | Velocity damping |
| `a_max` | 4.0 | Per-axis action limit |
| `init_speed` | 1.0 | Fixed magnitude of initial angular velocity |
| `mass` | 0.6 | Inertia divisor |

`reset()` independently samples `theta`, `phi`, and the direction of a fixed-magnitude initial
angular velocity. The environment stores `batch` trajectories in tensors and advances all of them
synchronously.

Primary implementation:

- `src/quickdraw/environments/torus.py`
- `conf/environments/torus.yaml`

## Current collection contract

### Action source

Actions come from a two-dimensional Ornstein–Uhlenbeck process:

```text
u <- u + 0.15 * (-u) + 0.4 * Normal(0, I)
action <- clamp(a_max * u, -a_max, a_max)
```

There is one `torch.Generator` per entire split. All parallel trajectories draw from it. Despite
older design prose, the current code does **not** fold the episode ID into an independent
per-episode seed.

### Temporal alignment

The generated arrays have equal length:

```text
observations: (episodes, steps, 6)
actions:      (episodes, steps, 2)
```

Their actual meaning is:

```text
observation[t] --action[t]--> observation[t + 1]
```

for `t < steps - 1`. A fresh action is sampled and appended at the final index only to make the
arrays equal length. That final action is not applied and has no successor observation.

This is a real schema hazard. The last row looks like a transition but is padding, and there is no
mask marking it as invalid. Correct counts are therefore:

```text
frames      = episodes * steps
transitions = episodes * (steps - 1)
```

`summary.json` currently reports `episodes * steps` as `"transitions"`, while training startup logs
use the correct `episodes * (steps - 1)`.

### No task lifecycle

All trajectories have fixed length. The current data contains no:

- reward;
- success or failure;
- `terminated` or `truncated`;
- semantic event or task phase;
- natural-language instruction beyond the constant LeRobot task string `"torus"`;
- contact, object, or privileged simulator state;
- camera calibration;
- action-validity mask.

## Current rendering contract

Every state is rendered from an egocentric camera on the torus:

- camera position: the particle's surface position;
- up direction: torus surface normal;
- forward direction: tangent velocity;
- heading smoothing: `0.85 * previous + 0.15 * current`, with a fallback near zero velocity;
- stored resolution: `256 x 256`, HWC `uint8`, MP4;
- base appearance: HSV-positioned torus texture;
- visual-OOD appearance: HSV texture plus gray circles.

PyVista/VTK performs the rendering. Dataset FPV clips use a fresh plotter for each frame. The
interactive/control renderer reuses a persistent renderer and is intentionally not byte-identical.

On load, the image path is decoded and area-downsampled to the model's requested square size
(currently 128), then cached as:

```text
<dataset-root>/<split>/fpv_128.npy
```

The cache is a derived local artifact, not part of the source dataset's declared version.

Primary implementation:

- `src/quickdraw/logging/viz.py`
- `src/quickdraw/data_generation.py`
- `src/quickdraw/data/dataset.py`

## Current persisted dataset

### LeRobot features

Each split is created as its own `LeRobotDataset`:

```text
repo_id = "torus/<split>"
root    = "<run-dir>/<split>"
```

| Feature | Type and shape | Status |
|---|---|---|
| `observation_vector` | `float32[6]` | Project-specific name |
| `action` | `float32[2]` | Conventional LeRobot name |
| `observation.images.fpv` | video, `uint8[256,256,3]` | LeRobot image namespace |
| `task` | constant `"torus"` | Special value supplied to `add_frame`; represented through LeRobot task metadata |

`observation.images.<camera>` and `action` are aligned with LeRobot conventions.
`observation_vector`, the fixed dimensions, the `torus/<split>` IDs, and one-dataset-per-split
organization are Quickdraw conventions.

LeRobot's internal Parquet/video/metadata layout is delegated to the installed LeRobot version. The
write and read API surfaces are intentionally isolated in:

- `write_lerobot_split()` in `src/quickdraw/data/generate.py`;
- `load_split_episodes()` and `load_split_episodes_mm()` in
  `src/quickdraw/data/dataset.py`.

This isolation is good, because `pyproject.toml` does not pin LeRobot. At this commit, `uv.lock`
resolves LeRobot 0.4.4 for Python below 3.12 and 0.5.1 for Python 3.12 or newer. Reproducibility
therefore depends on the selected Python version as well as the Git commit.

### Root metadata and media

A generation run has this conceptual layout:

```text
<run-dir>/
├── dataset_card.json
├── normalization_stats.json
├── summary.json
├── progress.log
├── train/                         # one LeRobotDataset
├── val/
├── eval_ood_horizon/
├── eval_ood_visual/
├── eval_ood_geometric/
├── eval_ood_dynamics/
└── media/
    ├── summary_plots/
    ├── summary_videos/
    ├── fpv/<split>/ep_XXXX.mp4    # source clips also ingested into LeRobot
    └── composites/
```

`normalization_stats.json` contains train-only flattened mean/std for
`observation_vector` and `action`. `dataset_card.json` records the base environment, resolved
per-split environment, coloring, split sizes, seeds, and FPS. `summary.json` repeats much of this
plus counts and training-window totals.

The run directory is treated culturally as immutable, but there is no checksum, manifest digest,
write protection, source commit field, simulator package lock, or content-addressed version
enforcing that immutability.

## Current generation and loading flow

Generation is:

```text
Hydra split config
    -> batched TorusEnv + OU sampling
    -> all vector trajectories held in memory
    -> split summary plots/videos
    -> one 256x256 FPV MP4 per episode in a process pool
    -> one LeRobotDataset per split
    -> root metadata and composite videos
```

Although the simulator supports a device argument, `data_generation.py` calls it without one, so
the current default generation path simulates on CPU.

Loading is:

```text
LeRobotDataset("torus/<split>", root="<root>/<split>")
    -> Hugging Face dataset rows as NumPy
    -> group by episode_index
    -> optional decode/downsample/cache of FPV videos
    -> pre-stack all P+F windows
    -> normalize vectors with train-only statistics
    -> place complete window stores on GPU
```

The yielded model batch is:

```text
obs_seq:   float32[B, P+F, 6]       normalized
act_seq:   float32[B, P+F, 2]       normalized
image_fpv: float32[B, P+F, H, W, 3] in [0,1], when configured
```

The model maps stored `observation_vector` to its modality name `proprio`. Images are optional, but
the current loader supports at most one image modality selected from the model configuration.

## What is reusable and what is hard-coded

### Reusable today

- A run-per-generation provenance boundary.
- Train, validation, and explicit OOD split concepts.
- Train-only normalization reused across evaluation splits.
- Episode grouping and temporal window construction.
- Low-dimensional plus video storage through LeRobot.
- Separation of vector simulation, rendering, and dataset writing.
- Batched simulator execution.
- An isolated read/write seam around a drifting LeRobot API.
- Single-axis OOD overrides in Hydra.

### Environment-specific today

- Direct imports of `TorusConfig`, `TorusEnv`, and `OUActionSampler`.
- `env_cfg()` constructing only `TorusConfig`.
- Fixed `observation_vector[6]`, `action[2]`, and `observation.images.fpv`.
- `Normalizer` knowing exactly two numeric streams.
- Loader assumptions about repo IDs, directory names, dimensions, and image count.
- Constant task name `"torus"`.
- The OOD split taxonomy.
- Torus geometry, renderer, metrics, goals, and controller.
- Evaluation code importing torus-specific `R`, `r`, normals, and signed distance.
- No environment registry, adapter, feature registry, schema version, or capability negotiation.

Conclusion: **LeRobot makes the files interoperable at the storage layer; it does not make the
generation or experiment code simulator-agnostic.**

## Current correctness and reproducibility debts

These should be resolved before presenting the data pipeline as a general benchmark protocol:

1. **Long-horizon evaluation reads the wrong split.** `eval_ood_horizon()` loads `val`, not
   `eval_ood_horizon`. With `P=8` and 256-frame validation episodes, the requested horizon is capped
   at 247 rather than using the generated 1,024-frame data.
2. **Three OOD evaluations silently skip current models.** `_openloop_split()` returns `{}` for a
   model with the multimodal layout. All current model constructors use that layout, including
   proprio-only variants, so visual/geometric/dynamics OOD are effectively pending.
3. **The final action is unmarked padding.** Consumers can accidentally treat it as a real
   transition.
4. **Transition counts disagree.** Generation summary counts frames as transitions; training logs
   count actual successor-bearing transitions.
5. **Documentation has drifted.** `design/data.md` and `design/environment.md` describe older
   dimensions, split sizes, FPS, horizons, seeding, render technology, loading, and environment
   defaults.
6. **Dependency resolution is Python-sensitive.** The dataset format implementation changes between
   LeRobot 0.4.4 and 0.5.1.
7. **No immutable dataset identity.** The metadata omits source commit, resolved package lock,
   generator version, content hashes, and host/render details.
8. **The LeRobot writer is not explicitly finalized.** The resolved Python 3.13 environment uses
   LeRobot 0.5.1 and exposes `LeRobotDataset.finalize()`, but `write_lerobot_split()` returns after
   `save_episode()` calls without invoking it. LeRobot's v3 documentation requires finalization to
   flush and close writers; this must be made explicit rather than relying on process teardown.
9. **No schema-level validation.** Counts and FPV alignment are asserted in places, but there is no
   end-to-end validator for determinism, temporal alignment, episode boundaries, action validity,
   split leakage, or replay.

## The environment-independent contract to adopt

The next implementation should separate five responsibilities:

```text
SimulatorAdapter
    owns reset/step, spaces, seeds, termination, privileged state, snapshot/restore

ActionSource
    owns random, scripted, teleoperated, expert, policy, or planner actions

ObservationRenderer
    owns cameras, calibration, RGB/depth/segmentation, and render metadata

TaskSemantics
    owns instruction, objects, skills, phases, events, rewards, and success predicates

MetricSuite
    owns open-loop prediction metrics, action adherence, closed-loop success, and OOD slices
```

The collector should depend only on these protocols plus a declarative dataset schema. Torus,
ManiSkill, LIBERO, and RoboCasa adapters should all produce the same collector-facing transition
object.

### Required simulator interface

Conceptually:

```python
class SimulatorAdapter(Protocol):
    id: str
    observation_space: SpaceTree
    action_space: Space
    capabilities: set[str]

    def reset(
        self,
        *,
        seeds: Sequence[int],
        options: Mapping | None = None,
    ) -> tuple[ObservationBatch, InfoBatch]: ...

    def step(self, action: ActionBatch) -> TransitionBatch: ...

    def close(self) -> None: ...
```

`TransitionBatch` must contain:

```text
next_observation
reward
terminated
truncated
info
```

The adapter may be natively batched, but a one-environment wrapper must be able to expose the
standard Gymnasium return contract. Snapshot/restore should be an optional declared capability for
counterfactual world-model evaluation.

### Canonical feature namespace

Required:

| Feature | Contract |
|---|---|
| `observation.state` | `float32[state_dim]`; observable robot/environment state, with component names and units |
| `action` | `float32[action_dim]`; component names, units, bounds, frame, and control mode declared |
| `reward` | Scalar environment reward, even if always zero |
| `terminated` | Task-defined terminal condition |
| `truncated` | Time/resource boundary |
| `transition.valid` | False on a final observation-only/padded row |
| `timestamp` | Monotonic seconds in the episode |

Conditionally required:

| Feature | When required |
|---|---|
| `observation.images.<camera>` | For each RGB camera used by the model |
| `observation.depth.<camera>` | When geometry is an experimental modality |
| `observation.segmentation.<camera>` | When semantic/object supervision is claimed |
| `observation.object_state` | When privileged state evaluation or object-centric modeling is claimed |
| `observation.contacts` | When contact reasoning is claimed |
| `success` | For task-oriented environments |
| `language.instruction` | For language-conditioned or semantic steering |
| `semantic.skill_id` | For compositional/hierarchical tasks |
| `semantic.phase` | For within-skill stages such as approach/grasp/transport/place |
| `semantic.event` | Sparse state changes such as grasp, open, insert, spill, collision |

LeRobot should remain the primary storage layer. Its conventional names
`observation.state`, `observation.images.<camera>`, and `action` should be used directly. Extra
semantics may live as numeric/categorical frame features or as episode metadata, but their encoding
and vocabulary must be declared in the manifest rather than inferred from filenames.

### Transition alignment rule

Retain equal-length per-frame arrays only with an explicit validity mask:

```text
row t:
    observation[t]
    action[t]
    reward[t]
    terminated[t]
    truncated[t]
    transition.valid[t]

if transition.valid[t]:
    applying action[t] to observation[t] produces observation[t + 1]
```

The last row may be the terminal observation with `transition.valid=false`. It must not contain a
fresh random action. Counts, windows, and losses must ignore invalid transitions.

Action timestamps also need a declared convention:

- command issue time;
- actuator application time;
- observation exposure interval;
- control frequency;
- whether an action is instantaneous, held until the next step, or an action chunk.

### Split policy

The split declaration must distinguish:

- **ID validation:** new seeds, same tasks/scenes/objects/dynamics;
- **held-out task:** new instructions or compositions;
- **held-out object:** known skills on unseen objects;
- **held-out scene:** known skills in unseen layouts/textures;
- **held-out dynamics:** friction, mass, latency, actuation, or camera changes;
- **long horizon:** more steps without conflating another shift;
- **counterfactual-action test:** common initial states replayed under deliberately divergent action
  sequences.

Each OOD split should alter declared axes only, with a validator comparing resolved configurations.

## Acceptance tests for every environment

A dataset/environment adapter is complete only when all of these pass:

1. Same adapter version, seed list, and action sequence reproduces the same low-dimensional
   trajectory within a declared tolerance.
2. Every valid `action[t]` replays to stored `observation[t+1]`.
3. Every invalid/final action is masked and excluded from transition counts and losses.
4. Observation/action values match declared spaces, units, names, and coordinate frames.
5. `terminated` and `truncated` are mutually interpretable and episode boundaries are exact.
6. Camera frame counts equal tabular frame counts; calibration and camera names are stable.
7. Train-only normalization is used on all validation/test/OOD splits.
8. No episode, initial-state seed, scene, object instance, or language paraphrase leaks across a
   split where it is declared held out.
9. Semantic skill, phase, event, and success labels agree with simulator predicates on a reviewed
   sample and a programmatic consistency suite.
10. Stored trajectories can be rendered/replayed independently of the training code.
11. A random policy and one competent baseline produce plausible, separable success distributions.
12. Closed-loop evaluation demonstrably loads the intended named split.
13. All enabled model families execute every declared evaluation rather than silently returning an
    empty result.
14. The manifest captures the Quickdraw commit, simulator revision, LeRobot version, and file
    digests.

## Migration plan

### Phase 0: repair the present experiment

- Make `eval_ood_horizon` consume `eval_ood_horizon`.
- Port OOD split evaluation to the current multimodal model interface.
- Add `transition.valid` and stop sampling an unused final action.
- Correct transition/duration summaries.
- Pin one Python and LeRobot version for generated datasets.
- Explicitly finalize each LeRobot dataset writer.
- Generate and validate a source/provenance manifest.

### Phase 1: extract the generic data boundary

- Add an environment registry and `SimulatorAdapter`.
- Move OU sampling behind `ActionSource`.
- Move torus FPV code behind `ObservationRenderer`.
- Replace fixed feature dictionaries with schema-driven features.
- Generalize normalization and loading over named numeric/image streams.
- Keep Torus output numerically equivalent, apart from the explicit final-transition fix.

### Phase 2: become Gymnasium-compatible

- Supply `observation_space`, `action_space`, `reset(seed, options)`, and the five-value `step`.
- Preserve the fast native batched implementation.
- Provide Gymnasium single and vector wrappers instead of forcing the simulator core into one
  execution model.

### Phase 3: add task semantics

- Add instructions, reward, success, skill, phase, events, objects, contacts, and camera metadata.
- Make semantic vocabularies dataset-versioned.
- Allow oracle simulator predicates and learned reward models to be evaluated side by side.

### Phase 4: add a robotics adapter

- First pass the contract against a small, deterministic robotics task.
- Then ingest a standard semantic benchmark without rewriting collector, storage, loader, or
  evaluator infrastructure.
- The selected robotics target and work breakdown are in `ROBOTICS-DATASET-TASKS.md`.

## Definition of "plug and play" for Quickdraw

An environment is plug and play only when adding it requires:

1. one adapter package;
2. one declarative schema/manifest;
3. optional renderer, task-semantics, and metric plugins;
4. configuration selecting the registered environment;

and requires **no edits** to the generic collector, LeRobot writer, window loader, model batch
assembly, experiment orchestrator, or shared evaluation loop.

Quickdraw does not meet this definition at commit
`1140bbcfd1435e6e82bc8193646343d261706244`. This document defines the boundary needed to get there.
